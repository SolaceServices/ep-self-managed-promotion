# solace

Everything in this folder is **produced by the GitHub Actions workflows**: configuration backups of the event
brokers, Terraform for the Solace Cloud services, and the Terraform applied for each Event Portal application.
The workflows commit these files back to the repository, so the git history of this folder is an audit trail of
what changed and when.

You normally do not edit these files by hand.

## Layout

│   ├── message-vpn/
│   │   └── sandbox/

│   │       └── sandbox.err.cli            Errors from that backup
│   ├── EmployeeLifecycleManager/          One folder per deployed Event Portal application
│   │   ├── .gitignore
│   │   └── application_config.tf          Terraform applied to the broker
│   └── Workday/
│       ├── .gitignore
│       └── application_config.tf
│

## cloud/

Terraform that describes the Solace Cloud services of the account, generated by
[`scripts/solace_generate_cloud_backup.py`](../scripts/README.md) and imported into Terraform state by the
`Backup Solace Cloud Services` workflow.

| File | Written by | Description |
|------|------------|-------------|
| `provider.tf` | the generator, only when missing | `terraform` block requiring `solaceproducts/solacecloud` and the `solacecloud` provider with `base_url`. The API token comes from the `SOLACECLOUD_API_TOKEN` environment variable. |
| `terraform-backend.tf` | copy of `terraform/terraform-backend.tf` | Empty S3 backend (`encrypt = true`, `use_lockfile = true`). Bucket, key and region are passed to `terraform init`. |
| `solacecloud_service.<name>.tf` | the generator, every run | One service. Contains the `solacecloud_service` resource, its `solacecloud_connection_endpoint` resources, `solacecloud_connection_endpoint_dns_name` resources and an `import` block for each. |
| `.gitignore` | committed | Ignores `.terraform/`, `.terraform.lock.hcl`, `*.tfstate*`, `tfplan`, `*.tfvars`, override files and crash logs. |

Naming:

- File: `solacecloud_service.<service-name>.tf`. The prefix lets scripts iterate over the services with the glob
  `solacecloud_service.*.tf`.
- Resource labels are built from the service name, then the endpoint name, then the DNS name, for example
  `solacecloud_service.my-service`, `solacecloud_connection_endpoint.my-service_Public_Endpoint`.
- Names that differ only by case (for example `ajcr-sandbox-primary` and `AJCR_sandbox_primary`) are different
  files. A file for a service that was renamed in Solace Cloud stays here until it is removed by hand.

What the generated resources contain: service name, data centre, service class, broker version, Message VPN name,
spool size, deletion lock, owner, DMR settings, mate-link encryption, optional environment, plus the connection
endpoints with their ports and custom DNS names. See the attribute mapping in
[scripts/README.md](../scripts/README.md#attribute-mapping).

Each resource has an `import` block (Terraform 1.5+). On the first apply Terraform adopts the existing object into
state; afterwards the blocks are no-ops.

## development/ and test/

Each folder corresponds to a GitHub Environment (and an Event Portal environment) of the same name.

### `broker.cli` / `broker.err.cli`

Output of `show current-config all redact` for the whole event broker, written by `backup_broker.yaml`. The file
starts with a header and a `! BEGIN` marker:

```
! BEGIN
! Command: "show current-config all redact"
! Generated by:
!   Username: "<cli user>"
!   Date: "<timestamp>"
!   Version: "<broker version>"
...
```

It is the Solace CLI configuration script, so it can be read as text, diffed between commits, or replayed on a
broker. Secrets are redacted by the broker. `broker.err.cli` holds anything received on stderr; the workflow fails
when it is not empty, so a committed file is normally empty.

### `message-vpn/<vpn>/<vpn>.cli` / `<vpn>.err.cli`

Same idea for a single Message VPN (`show current-config message-vpn <vpn> redact`), written by
`backup_message_vpn.yaml`. These are much smaller than the whole-broker backup and show VPN-level changes
(client profiles, ACLs, queues, bridges, and so on) clearly in a diff.

### `<application>/application_config.tf`

The Terraform configuration that was pushed to the broker for an Event Portal application, written by
`deploy_ep_application.yml`. It uses the `solaceproducts/solacebroker` provider:

- a `provider "solacebroker"` block with an alias per target, whose `url`, `username` and `password` come from the
  variables `var.url`, `var.username`, `var.password`;
- `data` sources for existing Message VPNs and client profiles (looked up, not created);
- `resource` blocks for objects the application needs, such as client usernames, ACL profiles and ACL publish topic
  exceptions.

```hcl
terraform {
  required_providers {
    solacebroker = {
      source = "registry.terraform.io/solaceproducts/solacebroker"
    }
  }
}

provider "solacebroker" {
  alias    = "id_xxxxxxxx"
  username = "${var.username}"
  password = "${var.password}"
  url      = "${var.url}"
  ...
}

data "solacebroker_msg_vpn" "id_xxxxxxxx" { ... }
resource "solacebroker_msg_vpn_client_username" "..." { ... }
```

The file is overwritten with each deployment. It contains no secrets, because credentials are supplied through
`TF_VAR_*` variables at run time.

`<application>/.gitignore` is copied from `terraform/.gitignore` and keeps state, plans, `.terraform/` and
`*.tfvars` out of git.

## How the files are produced

| Files | Workflow | Trigger | Committed by |
|-------|----------|---------|--------------|
| `cloud/*.tf` | `backup_cloud.yaml` | daily 21:50 `America/New_York`, or manual | `github-actions[bot]`, message `Update generated backup files` |
| `<env>/broker.cli`, `<env>/broker.err.cli` | `backup_broker.yaml` | daily 22:10 `America/New_York`, or manual | `github-actions[bot]`, message `Update generated backup files` |
| `<env>/message-vpn/<vpn>/*.cli` | `backup_message_vpn.yaml` | daily 22:00 `America/New_York`, or manual | `github-actions[bot]`, message `Update generated backup files` |
| `<env>/<application>/application_config.tf`, `.gitignore` | `deploy_ep_application.yml` | manual | `github-actions[bot]`, message `Update generated files after deployment` |

A commit is only made when something changed; otherwise the workflow prints `Nothing to commit`. State files and
`.terraform/` are removed from the git index before every commit, so they are never pushed.

Because the workflows push to the repository, the working branch must allow pushes from `github-actions[bot]`
(the workflows have `contents: write`).

## Terraform state

State is stored remotely in the S3 bucket named by the `AWS_BUCKET_NAME` secret. It is never kept in this folder.

| Folder | State key in the bucket |
|--------|-------------------------|
| `cloud/` | `solace/cloud/terraform.tfstate` |
| `<env>/<application>/` | `solace/<env>/<application>/terraform.tfstate` |

Each application therefore has its own independent state per environment, which is why a failed deployment can
safely run `terraform destroy` without touching other applications.

If you run Terraform locally in one of these folders, local files such as `.terraform/`, `.terraform.lock.hcl`,
`tfplan` and `terraform.tfstate` can appear. They are ignored by the folder's `.gitignore`.

## Reading the backups

- **What changed?** Use `git log -p -- solace/development/broker.cli` or compare two commits. Because the output is
  redacted and ordered by the broker, normal day-to-day edits show up as small, readable diffs.
- **Which Cloud services exist and how were they configured?** Open `cloud/solacecloud_service.<name>.tf`.
- **Which configuration was last deployed for an application?** Open `<env>/<application>/application_config.tf`;
  `git log` shows each deployment.
- **Recreate a service.** Apply the files in `cloud/` against a state that does not contain the service. Remove
  the `import` block of the service you want to create from scratch, otherwise Terraform tries to adopt the
  original one.

## Adding an environment, application or VPN

| To add... | Do this |
|-----------|---------|
| **An application** | Run `Deploy Event Portal Application` with the new `application_name`. The folder `solace/<env>/<application>/` is created automatically. |
| **A Message VPN backup** | Add the VPN name to the `msg-vpn` list in the matrix of `backup_message_vpn.yaml`. |
| **An environment** | Create the GitHub Environment with its secrets and variables, add it to the `environment` input options of `deploy_ep_application.yml` and to the matrices of the two backup workflows. |
| **A Cloud service** | Nothing to do if `SOLACE_CLOUD_SERVICES` is empty (all services are exported). Otherwise add its name to that comma-separated variable. |
